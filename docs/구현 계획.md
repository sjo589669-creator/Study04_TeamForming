# 구현 계획

## 1. 구조
```
streamlit_app.py          화면(로그인, 학생 화면, 관리자 화면). key 는 공고 2.7절 그대로
teamforming/rules.py      규칙만 담은 순수 함수(지원 검사, 배정안 검사, 모든 경우 탐색 배정, 배정 불가 이유)
teamforming/store.py      DB 읽기·쓰기와 지원/투표/마감/확정 처리(트랜잭션, 행 잠금)
teamforming/ai.py         오픈라우터 호출(1·2·3차, 모델마다 전체 120초), 응답 해석, 실패 처리
schema.sql                tf_ 테이블과 제약. 앱이 시작할 때 이 파일을 그대로 실행
.github/workflows/keepalive.yml   매일 DB 질의(Supabase 일시정지 방지)
tests/run_scenarios.py    연습용 시나리오 3개를 단계별로 실행해 기대 결과와 비교
```

## 2. 단계
| 단계 | 내용 | 확인 방법 |
|---|---|---|
| 1 | schema.sql: 최소 참고안 + 지원 시각·결정 시각·거절 이유, 대기 지원 1개 부분 유일 인덱스, tf_ai_logs | 로컬 PostgreSQL 에서 실행 |
| 2 | rules.py: `join_block_reason`(정원, 주 역할, 필수 역할 자리), `required_filled`(기획자·웹 프로그래머를 서로 다른 학생으로 셀 때 채운 수) | 시나리오 단계별 결과 |
| 3 | store.py: 명단 올리기(utf-8-sig), 지원, 투표(거부 즉시 거절, 전원 찬성 시 승인 직전 재검사), 마감 | 시나리오 3개 |
| 4 | rules.py: 배정안 검사 5가지, 백트래킹으로 모든 경우 탐색, 배정 불가 이유 | 배정 불가 사례, 3차 실패 사례 |
| 5 | ai.py: 작업 스레드에서 요청, 화면은 0.5초마다 경과 표시, 120초 넘으면 버리고 다음 모델 | 느린 가짜 응답으로 시간 제한 확인 |
| 6 | streamlit_app.py: 로그인(bcrypt), 학생 화면 fragment, 관리자 화면, 결과 안내 | 로컬 실행 후 연습 시나리오 직접 해 보기 |
| 7 | 배포: Streamlit Community Cloud, Secrets, 공개 설정 | 시크릿 창에서 로그인 화면 확인 |
| 8 | keepalive: GitHub Actions 에 DATABASE_URL 등록, 수동 실행으로 확인 | Actions 실행 기록 |

## 3. 동시성
- 지원·투표는 `tf_settings('closed')` 를 `FOR SHARE`, 해당 팀 행을 `FOR UPDATE` 로 잠근 뒤 검사 → 같은 팀 처리가 차례로 일어남
- 마감은 `closed` 를 `FOR UPDATE`, 모든 팀 행을 잠근 뒤 처리 → 마감과 승인이 엇갈리지 않음
- 그래도 생길 수 있는 마지막 자리 경쟁은 `(team_id, slot_no)` 기본 키와 `student_id` 유일 제약이 막음

## 4. 배정 흐름
1. 모든 경우 탐색으로 규칙을 지키는 배정이 있는지 먼저 확인 → 없으면 이유를 보여 주고 끝(AI 호출 없음)
2. 1차 → 2차 → 3차 모델. 실패 이유와 걸린 시간은 화면(assign_status)과 tf_ai_logs 에 남김
3. 3차까지 실패하면 1번에서 찾은 배정을 씀
4. 배정안은 tf_settings('proposal') 에 저장, 확정할 때 지금 상태로 다시 검사한 뒤 tf_members 에 넣음
